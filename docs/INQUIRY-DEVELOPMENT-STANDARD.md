# 询盘与页面开发、验收及发布规范

版本：2026-09-02。适用：中谷独立站所有新建、改版和重新发布的页面，包括首页、车型、车型列表、地区/语言专题，以及 WhatsApp 询价弹窗。

本文件是后续开发的强制检查清单，不是某次发布已完成的证明。生产版本和实际验收结果必须另记在 `ops/seo/` 发布报告中。晨检执行、安全及认证规则以 `ops/daily-check/RUNBOOK.md` 为唯一规范；本文件不得放宽其中的限制。

## 1. 全球号码与客户国家完全分离

- 客户所在国家、车辆目的市场/目的港、电话号码所属国家是三个不同信息。不得互相覆盖，不得要求一致。
- 任意国家的客户均可使用任意受支持国家/地区的有效 Phone / WhatsApp 号码。阿尔及利亚客户使用美国或西班牙号码只是示例，不是特例或白名单。
- 支持两种输入：选择号码区号后填写本地号码；直接填写以 `+` 或 `00` 开头的完整国际号码。
- 完整国际号码按号码自身区号解析。地区页面的预选值仅是便利选项，必须可以更改。客户国家/目的市场不随号码变动。
- 不得一律删掉前导 0 或简单拼接区号。埃及、伊拉克、伊朗等地国内拨号前缀与意大利需要保留的 0 必须按元数据处理；不能凭数字开头猜测后截断。
- 接受阿拉伯语数字、波斯语数字和全角数字，统一保存规范国际号码。不得擅自把有效固话/VoIP 号码排除为无效 WhatsApp。
- 格式校验不证明号码所有权、实际可达性或 WhatsApp 注册状态。不得宣称已验证上述事实；需要短信或外部验证时另行取得授权。
- 当前号码规则库覆盖 245 个国家/地区。元数据升级后重新核对覆盖范围，不把该数字作为永远不变的产品承诺。

### 共用实现，禁止复制各国特例

- 规则源：`scripts/lib/phone.js`，使用锁定版本的 `libphonenumber-js/max`。
- 浏览器产物：`assets/js/phone-input.js`；由 `scripts/build-phone-input.js` 生成，不手工编辑压缩产物。
- 服务端：`netlify/functions/inquiries.js` 使用同一规则源再次验证。仅修 HTML pattern 不算完成。
- 普通表单与 `assets/js/whatsapp-lead-modal.js` 必须保持同一标准。
- 号码库从本站加载，不新增第三方号码查询、CDN、验证码或强制外部连接。更新时保留许可证和依赖锁文件。
- `country` / `market` 保存客户/采购目的信息；`countryCode` / `whatsappLocal` / `phoneCountry` 保存号码信息。不得用 `phoneCountry` 回填或校验限制 `country`。
- CRM 现有 `whatsapp` 字段使用规范号码的纯数字形式，浏览器规则返回 E.164 带 + 形式；转换只能发生在明确的存储边界，不重复加区号。

## 2. 新增页面接入合同

优先复用现有车型/地区生成器和表单结构，不重新实现一套提交逻辑。

1. 普通表单保留 `form.inquiry-form`；字段包括姓名、客户国家、号码区号、号码、车型/需求，以及可选邮箱、港口、预算。沿用已支持的字段映射。
2. 区号使用 `calling_code`，号码使用 `phone_number`，兼容隐藏 `whatsapp`。维护来源页面、页面 URL、语言、市场和车型 ID 等归因字段，不能因号码来自外国而改归因。
3. 全局区号列表来自规则库，不能恢复为少数重点市场的硬编码列表。保留可自由选择及完整国际号码输入。
4. 必须显示“号码区号可以与客户国家或收货地不同”的说明，必要时本地化。
5. `phone-input.js` 必须先于依赖它的公共脚本执行；保留正确的 defer/加载顺序。不要把“HTML 有表单”当作“提交处理已绑定”。
6. HTML pattern 采用现代 Unicode v 兼容写法；不得复制旧的 `[0-9 ()-]{5,20}`。构建后和真实浏览器中均验证，不只检查正则字符串。
7. 未加载规则库、无效号码、必填项缺失、邮箱格式错误，均不能进入普通提交。对用户给出可理解的提示，不把失败吞掉。
8. 所有字段、提示及按钮在 390px 宽度下可使用、不横向溢出；国家列表长名称也不能撑破页面。
9. 无内嵌表单的页面必须有明确询价入口。不能因“链接可见”便声称已验证后台送达。

## 3. 提交与重试

- 普通 JavaScript 表单以 CRM API 的持久化成功为成功条件。成功后完成页面流程，不再额外向 Netlify Forms 重复 POST。
- 不允许“CRM 已保存，但第二条通道失败导致提示整体失败”的实现。
- CRM 不可用/结果不明确时，不能盲目降级到另一个写入端点。保留用户输入和可重试状态。
- 提交中禁用重复触发；为同一次请求保留随机 submissionId，顺序重试不重复建单/触发 Webhook。更改为新需求时不能错误复用旧请求。
- 当前顺序重试保护不等于数据库级并发 exactly-once。涉及存储架构变更时单独设计并发与恢复测试。
- 保留历史 Netlify Forms 导入兼容，不未经批准迁移、删除或重分类既有客户。
- 本任务不授权修改销售报价。价格以经用户确认的车型数据为准；本次 Full Option 仍为 FOB US$11,500。

## 4. 测试隔离：失败时禁止写入

严格执行 RUNBOOK 的认证预检 → 精确查重 → 允许时单次隔离提交 → 再次核验顺序。

- 固定元数据：`is_test=true`、`test_type=daily_morning_check`、`test_id=AUTO-TEST-YYYYMMDD-<ENTRY>`。日期按北京时间，入口只用已配置值。
- 测试姓名、号码、邮箱只能用项目配置的固定身份。不得拿真实客户、随机可达号码或个人邮箱提交测试。
- 管理员身份或服务端 secret 必须在服务器验证；公开伪造测试字段不能获准。不得索取/记录密码、Cookie、令牌或会话。
- 每天每个入口最多一条；精确已有记录则只读并跳过，不再次 POST。不能仅凭姓名或模糊关键词判断。
- 401、登录页、查重请求失败、返回结构不明、标记不符、多条重复、外部动作抑制未确认：禁止写入；不得降级为普通询盘。
- 前端允许固定测试号码的例外，只能限于有效标记模式；普通号码校验不得因此放宽。例外不替代服务端认证与查重。
- 测试记录默认不出现在客户列表、点击列表、业务统计及 CSV/客户备份中；独立入口 `/admin/test-inquiries.html` 只读展示。
- 服务端禁止对测试记录联系、分配、改状态、备注、删除或发送通知；UI 隐藏按钮不等于服务器已隔离。
- 带 `daily_test_id` 的页面：WhatsApp 点击、弹窗、备用处理器均不能创建普通点击或询盘记录，不能打开外部会话。弹窗只能显示隔离提示，测试通过普通表单隔离通道执行。
- 检查请求 URL 或 body 中的测试标记，拒绝进入非隔离 API 分支。标记格式错误也不能被当成普通用户提交。
- 不访问 `/crm/`，不联系测试记录，不清除或覆盖真实客户数据。

### 已批准历史测试记录的恢复

- 历史记录恢复不是每日新增测试；必须另有明确批准，按精确 ID、固定身份、原始日期和来源交叉核对，不按姓名模糊批量迁移。
- 2026-09-03 两条历史记录使用 `scripts/lib/approved-test-recovery.js` 中的固定清单。管理员恢复入口为 `/admin/test-recovery-20260903.html`，先认证、只读预检及快照指纹核对，再单次确认；无权限、身份不符或快照变化时不写入。
- 此恢复只写服务端独立登记 `approved-test-isolation-20260903.json`，不覆盖客户总表。读取时仅对符合固定清单和身份的两条记录恢复测试属性，保留原数据；旧 Forms 回导不能移除该登记。
- 不得扩大该清单或把其他历史数据自动归类。新目标必须另行核实和获准。后续重构导入、统计、导出或备份时必须继续经共享读取规则，避免绕开已生效的隔离登记。
- 本地测试需复现旧 Forms 合并覆盖标记的情况，并验证恢复后再次回导仍隔离；伪造身份、重复编号、过期预检和重复执行必须分别测试。测试凭证及存储必须完全模拟，不影响其他测试或生产环境。

## 5. 手机、桌面与语言验收

新增/修改页面至少检查：

- 桌面布局、390px 手机布局；有 RTL 语言时检查阿拉伯语/波斯语方向、标签、错误提示及区号可读性。
- 姓名等必填拦截、短号码及字母拒绝、错误邮箱拦截、有效本地号码、完整国际号码、与客户国家不同的号码。
- 代表号码覆盖国内前导 0、需保留 0、共享区号、阿语/波斯语数字，以及主动更换区号。
- 表单提交处理实际绑定；成功、失败、重试、重复触发和测试认证失败路径均有测试。
- 报价入口跳转、手机菜单跳转后收起、Escape/焦点行为、车型图库、询价弹窗关闭按钮。
- 阿语切换不能只改 RTL 或导航；实际修改范围内的标题、表单标签、提示应完整。不得把部分界面翻译说成整站翻译完成。
- 明确区分浏览器手机模拟、真实触控和实体 iPhone/Android；没有测过不能标为通过。

全站改公共表单或脚本时，按当前 sitemap 的全部带表单页面复测，不只抽样。2026-09-02 基线为 123 个规范页，其中 118 个普通表单页、5 个仅询价入口页；以后以实际数量为准。

## 6. 自动检查门槛

在拟发布版本中顺序执行：

```text
npm run build
npm test
npm run check:site
```

- 构建必须包含号码资源生成及共享资源内容版本更新。
- `tests/global-phone.test.js` 覆盖全地区示例、60,025 个跨地区组合、浏览器/服务器共用规则和生成页面合同。
- `tests/inquiry-repair.test.js` 覆盖跨国号码不修改市场、无效号码先于保存被拒绝、重试、测试查重/熔断、禁止测试写入及独立统计/导出。
- 既有价格、SKU、canonical、重定向、sitemap、语言交叉链接、晨检测试也必须继续通过。
- 单元测试只用内存存储和模拟外部请求；运行测试不得连接生产客户存储或真实 Webhook。
- 不得删掉失败测试、放宽断言或把未知结果改为成功来通过发布门槛。

## 7. 缓存、构建与发布

- 不直接编辑构建后的压缩号码包。修改源文件后完整构建，保留许可证。
- 所有改动的公共脚本/样式及动态加载的 WhatsApp 脚本都要内容版本化。只改文件却不更新长期缓存引用，不算发布完成。
- 版本化导致许多页面仅改引用时，报告中说明实际业务改动与机械更新数量；不得包装成许多新 SEO 内容。
- 发版基于远端最新已确认版本。工作区有他人/未整理改动时，使用独立分支/发布副本；不 reset、覆盖或混入无关改动。
- 提交前核对实际差异、文件清单、价格数据及测试结果。发布前再读取远端，确认快进；远端新增改动则停止并复核。
- 必须取得明确的生产发布许可。安全审核暂停时不得绕过；补丁若超出已批准范围，重新说明并确认。
- 提交/推送成功不等于线上生效。检查正式域名实际返回的页面、脚本版本、号码资源、价格和关键链接。
- 生产验证避免创建普通客户/点击记录；需要测试提交时只能走上述隔离通道，且遵守当天去重。
- 不擅自提交 sitemap、请求索引、点击搜索平台“验证修复”，不保证 SEO 排名。

## 8. 每次交付必须保留的记录

在 `ops/seo/` 保存独立、脱敏的修复/发布报告，至少包括：

- 分支、发布提交、部署及检查时间、真实上线/待发布状态；
- 修复内容、影响范围、未改变的报价/客户数据；
- 构建/测试结果和页面数量，桌面/手机实际覆盖；
- 数据来源、网络节点与限制；机房 HTTP 通不能代表当地所有手机网络；
- 本次生产提交数、测试复用/跳过原因、是否有任何外部动作；
- 未完成项、需批准项、回滚版本及已知风险。

禁止报告中出现客户完整联系方式、会话、密钥或未经核实的 CRM 数量。旧晨检成功不能充当新版本送达成功；本地验证不能充当生产验证。
